## Issue #28 — DNS readiness and offline-recovery diagnostics

Findings: `/healthz` returns a constant 200 (`cmd/dns-agent/main.go` `healthServer`). The hot-path writers (`QueryLogWriter.Write`, `LiveTap.Write`) drop rather than block; forwards are bounded (per-upstream timeout, 5 s budget) and single-flight waiters inherit that bound. No permanent stall is visible in the source, so this work makes state observable and pins recovery down with tests rather than guessing a fix. The image is distroless (no shell/curl), so a Docker `HEALTHCHECK` must use the binary itself.

### Task 1: Built-in probe record (`internal/resolver`)

- [ ] `ProbeName = "probe.mazedns.internal."`. `Resolver.Handle` answers it first — before control-plane-only, maintenance, rate limit, policy, cache and forward — with `A 127.0.0.1`, TTL 0, authoritative. Never forwarded, never recorded (no stats, no query log, no live tap).
- [ ] Tests: answered with no upstreams configured; answered over UDP and TCP via a real `Server`; does not bump `StatsSnapshot` or call `OnQuery`; answered in maintenance mode (the listener is what is being probed — readiness reports maintenance separately).

### Task 2: Resolver and listener health state

- [ ] `Resolver` tracks, as atomics: last query served, last successful forward, last failed forward + its error text. Timestamps are written at most once per second (load-compare before store) to avoid cross-core cache-line contention.
- [ ] `Resolver.Health() ResolverHealth` returns a snapshot.
- [ ] `Server` records whether its UDP and TCP listeners are bound: `Server.Listening() (udp, tcp bool)`.
- [ ] Tests for forward OK / failure bookkeeping.

### Task 3: Control-plane sync state (`internal/cluster`)

- [ ] `cluster.SyncHealth` (atomics: last success, last failure, last error). `Agent.SetSyncHealth(h)`; `syncOnce` records success (including 304 Not Modified) and failure.
- [ ] Created in `main` so `/readyz` can report it even before enrollment completes; standalone mode reports `"standalone"`.
- [ ] Test: failed fetch records failure; later success records success.

### Task 4: `GET /readyz` + `-healthcheck` (`cmd/dns-agent`)

- [ ] `/readyz` queries the agent's own DNS listener for `ProbeName` over UDP **and** TCP (1 s timeout each), at the listen address (wildcard → loopback).
- [ ] 200 when both answer and not in maintenance; 503 otherwise. JSON body: `ready`, `udp`, `tcp`, `maintenance`, `last_query`, `last_forward_ok`, `last_forward_error` (+ `error`), `control_plane` (`last_sync_ok`, `last_sync_error`, `error`, or `standalone`). WAN / control-plane state is informational and never fails readiness.
- [ ] `/healthz` unchanged (liveness), documented as such.
- [ ] `dns-agent -healthcheck`: loads the same config, GETs `/readyz` on loopback, exits 0/1. Dockerfile `HEALTHCHECK` for the agent target.
- [ ] Tests: `/readyz` 200 with a live server, 503 when the listener is down, 503 in maintenance; body fields present.

### Task 5: Offline / recovery tests

- [ ] Blackholed upstream (UDP socket that never replies): public queries fail with SERVFAIL within the configured budget; local rewrites keep answering fast throughout, including under many concurrent queries.
- [ ] Upstream restored (same address answers again): forwarding recovers without restarting the resolver.
- [ ] Serve-stale during the outage: an expired cached record is still served.
- [ ] Control plane unreachable: agent records sync failures, keeps serving the persisted policy, and records success once the control plane comes back.

### Task 6: Docs

- [ ] `docs/troubleshooting.md`: liveness vs readiness; watchdog guidance (probe `probe.mazedns.internal` locally, several consecutive failures, cooldown between restarts; a public lookup failing during a WAN outage is expected); Docker does not restart unhealthy containers by itself; split-DNS router mismatch; what to capture before restarting.
- [ ] `docs/install.md`: k8s `readinessProbe` → `/readyz`; mention the Docker healthcheck. `docs/configuration.md` / README: `/readyz` listed beside `/healthz`.

## Issue #29 — API tokens

**Open decision (ask before starting):** besides users / tokens / password / SSO + CP settings / metrics token / setup, should config import/export, enrollment keys and node management also be cookie-only? Recommendation: yes.

### Task 7: Store

- [ ] `api_tokens(id TEXT PK, name, token_hash UNIQUE, role, created_by, created_at, last_used_at, expires_at NULL)` in the schema list (fresh + existing DBs via `CREATE TABLE IF NOT EXISTS`).
- [ ] `CreateAPIToken`, `ListAPITokens`, `DeleteAPIToken`, `GetAPITokenByHash`, `TouchAPIToken` (write at most once a minute per token).

### Task 8: Auth path

- [ ] `SessionUser` gains `Kind` (`session` | `token`) and `TokenID`.
- [ ] `UserFromRequest`: an `Authorization` header is judged alone (`Bearer mzd_…`, known hash, not expired → token principal; anything else → unauthenticated, even with a valid cookie). Otherwise the cookie path as today. Tokens never set cookies.
- [ ] `requireSession(minRole, h)`: like `requireRole` but 403 for token principals. Applied to users, tokens, `/api/auth/password`, `/api/settings/cp`, metrics-token, (+ the routes from the open decision).
- [ ] `currentUser` / `auditUser` attribute token requests as `token:<name>`.

### Task 9: Endpoints + UI

- [ ] `GET /api/tokens`, `POST /api/tokens` (returns `mzd_` + base64url(32 random bytes) once), `DELETE /api/tokens/{id}` — admin, cookie session only.
- [ ] Web: "API tokens" section under admin Settings — list (name, role, last used, expiry), create dialog showing the value once with copy, delete.

### Task 10: Tests + docs

- [ ] Cookie only; token only; both (header wins); bad header + valid cookie → 401; revoked → 401; expired → 401; readonly token GET ok / write 403; admin token rewrite CRUD; cookie-only routes 403 with a token; works with SSO-only mode.
- [ ] `docs/user-guide.md`: "API tokens" section with a `curl` example.
